# Feature Specification: YUAUY Wallpaper 完整桌布應用程式

**Feature Branch**: `rust_build`

**Created**: 2026-10-31

**Status**: Draft — 共用不重複取圖與空來源處理已確認，待釐清空來源恢復觸發時機

**Input**: 將 `master` 的 C# GDI+ 桌布樣品重製為 Rust + DirectX 的完整 Windows 11 桌布應用程式，保留既有動畫和多螢幕行為。所有螢幕共用一個圖片來源與不重複隨機取圖佇列；每輪取完才重新掃描目錄並建立下一輪順序。有效圖片數至少為 1 時，跨輪可再使用相同圖片；有效圖片數為 0 時不執行任何圖片渲染，系統匣提示「沒有圖片」。透過系統匣與 YAML 設定。首次啟動在每一個螢幕先呈現一張位於畫面中央的主圖，再在每個螢幕各讓 10 張背景圖片以重疊進行、帶有隨機起始時間差的滑入效果，排至各自主圖背後並填滿背景；即每個螢幕共 11 張圖。啟動場景完全略過 GPU/CPU 負載檢查；這是使用者核准取代舊版快速初始化的新開場。後續平時維持靜態桌布並等待輪播時間到期；僅在準備開始下一張圖片的過場前檢測一次整體 GPU 使用率，超過門檻就跳過當次繪製，不建立獨立負載監測程序。WindowsEnv 25H2 使用 CPU/軟體繪圖驗證。

## Clarifications

### Session 2026-10-31

- Q: 舊版動畫的驗證參考是哪個入口？ → A: 使用者不確定；已靜態調查：`Form1.MainLoop` 與最新版 `Program.Main` 共有相同動畫核心（排除註解逐行一致），以該共同核心的公式、畫面操作和多螢幕規則為規格基準；`Form1` 的顯示配置更新為技術參考。現行啟動流程未能證實能自動輪播，不能將其視為已驗證；詳見 [舊版原始碼稽核](reference-audit.md)。
- Q: GPU 高負載的判斷範圍？ → A: 系統整體 GPU 使用率；WindowsEnv 沒有 GPU 時，改用系統整體 CPU 使用率進行測試。
- Q: 各螢幕圖片來源應如何分配？ → A: 所有螢幕共用一組圖片來源，各螢幕仍維持各自的畫面狀態與舊版的面積加權選取規則。
- Q: GPU 使用率何時檢測？ → A: 僅在等待到下一張圖片的預定繪製時間、準備進入過場前，當次檢測一次；待機期間不運行獨立負載監測／定期抽樣程序，也不做持續動畫繪製。
- Q: 當輪播期限已到，但高負載導致本次動畫被跳過時，何時再試？ → A: 選項 A；從本次高負載判定且跳過過場的時刻起，等待完整的正常輪播間隔，下一個期限到才再檢測一次；不設定縮短重試間隔或補播。
- Q: 首次啟動要沿用舊版加速播放多張相片嗎？ → A: 不沿用舊版因 GDI+ 效能限制而實作的快速輪播；先顯示中央主圖，再讓 10 張背景圖片以有隨機時間差的重疊滑入動畫移動至主圖後方，讓背景被相片填滿。一般輪播動畫公式維持不變。
- Q: 高負載門檻及相關排程值應如何設定？ → A: 全部使用使用者可編輯的 YAML 設定，包括正常輪播間隔、高負載暫停門檻與恢復門檻；不設定背景檢測週期。

### Session 2026-11-01

- Q: 新版多螢幕開場要各自顯示幾張圖片？ → A: 每個螢幕各一張中央主圖，背景數量取舊版 `Screen.AllScreens.Length * 10` 中的「每螢幕 10」意圖，固定為每螢幕各 10 張背景，共 11 張／螢幕。原始碼實際是全域計數器與面積加權隨機選螢幕，正常且圖片足夠時快速階段共 `10 × 螢幕數 + 1` 次換圖，並不保證每螢幕剛好 10 次；新版各螢幕確定配額是經使用者核准的新開場行為，詳見 `reference-audit.md`。
- Q: 首次啟動時 GPU 已經處於高負載怎麼辦？ → A: 首次啟動完全忽略 GPU/CPU 使用率，即使高負載也直接完成各螢幕的開場主圖與背景滑入；開場期間不需讀取使用率。開場完成、進入正常輪播後，才按 YAML 門檻於下一次輪播到期時讀取一次使用率。
- Q: 共用圖片少於開場所需張數，應重複使用還是減少開場圖片？ → A: 參考原始 `ImagePicker`，所有螢幕與開場／輪播共用一個不重複隨機取圖序列；每輪的所有可用圖片取完才重置，重置時更新目錄與下一輪順序。若至少有 1 張有效圖片，可以在完成一輪後重新使用，確保開場照常取圖；0 張則完全不繪製圖片，系統匣顯示「沒有圖片」。
- Q: 圖片列表何時重新掃描？ → A: 依使用者指定的循環邊界重新讀取圖片資料夾；不沿用舊版在每次 `Next()` 都比較資料夾檔案數量的做法。若 YAML 圖片目錄被使用者主動重新載入，應重新初始化來源；空資料夾的後續自動恢復時機仍待確認。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 保留舊版效果的 Windows 動態桌布 (Priority: P1)

使用者執行程式後，能在 Windows 11 桌面圖示後方看到輪播的圖片。每次切換保留既有動態效果與跨多螢幕的相片放置方式，而不是普通幻燈片。

**Why this priority**: 不還原舊版已驗證效果，Rust 重製就失去主要價值。

**Independent Test**: 使用固定圖片、固定隨機種子及單／雙螢幕幾何資料，比對最新版兩個 C# 入口共同的動畫核心之曲線、時間分段、畫面位置、轉換狀態及螢幕選取。再於 WindowsEnv 實際啟動 Rust 程式，確認桌布不是一般置頂視窗；舊版入口未直接驗證可正常自動輪播，須依原始碼稽核明確標示。

**Acceptance Scenarios**:

1. **Given** Windows 11 桌面與有效圖片來源，**When** 啟動應用程式，**Then** 在桌面圖示後呈現圖片而不妨礙其他視窗操作。
2. **Given** 多個尺寸與座標不同的螢幕，**When** 切換相片，**Then** 依既有螢幕面積加權規則選取目標螢幕，保留各螢幕已顯示圖片的狀態。
3. **Given** 固定的動畫進度與輸入參數，**When** 計算過場，**Then** 動畫的曲線、分段、平移、旋轉、縮放與覆蓋行為等價於舊版。
4. **Given** 顯示器接上、移除或變更解析度，**When** 顯示配置改變，**Then** 桌布重新建立正確的畫布，不遺留遮擋桌面的失效視窗。

---

### User Story 2 - 主圖優先的交錯滑入開場 (Priority: P1)

啟動時每個螢幕先看到居中的一張主圖；隨後每個螢幕各有 10 張其他相片從畫面外或預定進場位置滑入自己的主圖後方，動作在時間上彼此重疊，但各自帶有隨機起始延遲，使每個螢幕背景逐漸被相片填滿。這是每螢幕 11 張、全部螢幕共用相片來源的初始化場景。啟動時完全忽略 GPU/CPU 高負載。啟動開場不沿用舊版加速播放數十張的方式；完成後才進入既有輪播及低活動待機。

**Why this priority**: 使用者明確將開場視為新版應有的視覺效果，並批准其作為舊版啟動階段的替代設計；一般輪播動畫仍受原版等價性約束。

**Independent Test**: 以固定圖片與固定隨機種子，錄製開場並追蹤圖層、時間和圖片狀態：每個螢幕主圖先於背景可見、各有 10 張背景候選進場、背景相片能同時處於動畫中但啟動時間不完全一致、背景位於該螢幕主圖後方、完成後沒有永久繪製迴圈；模擬 GPU/CPU 使用率超過門檻時，開場仍執行且使用率讀取次數為 0。

**Acceptance Scenarios**:

1. **Given** 圖片來源有足夠有效相片，**When** 第一次啟動且桌面背景視窗已準備好，**Then** 每個螢幕各首先顯示一張中央主圖，而不是逐張快速輪播數十張。
2. **Given** 各螢幕主圖已出現，**When** 開場場景開始，**Then** 每個螢幕各有 10 張背景相片以滑入方式進入該螢幕主圖後方，部分動畫時間互相重疊，進場起始時間有可重現的隨機差異；兩個螢幕有足夠有效照片時，總計顯示 22 張。
3. **Given** 開場滑入已完成，**When** 進入正常待機，**Then** 主圖與已加入的背景圖停留在畫面上，不持續重新繪製，等待下一次正常輪播排程。
4. **Given** 開場完成，**When** 正常輪播時間到且負載允許，**Then** 後續圖片切換遵守既有 C# 動畫公式及多螢幕面積權重，不改用新開場的滑入動畫。
5. **Given** 程式首次啟動時整體 GPU（或 WindowsEnv 的整體 CPU）使用率已超過 YAML 門檻，**When** 開場開始，**Then** 仍完成各螢幕主圖與 10 張背景滑入；整個開場不做負載採樣，之後第一個正常輪播到期才啟用負載閘門。

### User Story 3 - 使用系統匣與 YAML 管理桌布 (Priority: P2)

使用者不需開著大型控制視窗即可常駐桌布程式；透過系統匣可檢視狀態、開啟設定檔、重新載入設定、暫停／繼續輪播，以及正常離開。圖片來源與輪播參數保存在 YAML。

**Why this priority**: 這是完整桌布工具與舊版實驗程式最大的使用體驗差異。

**Independent Test**: 在一台 Windows 11 電腦手動建立有效 YAML、從系統匣要求重新載入，再輸入無效 YAML 驗證錯誤回報與既有設定仍有效。

**Acceptance Scenarios**:

1. **Given** 使用者已有合法設定，**When** 開啟桌布程式，**Then** 設定生效且可在系統匣找到程式。
2. **Given** YAML 設定已編輯，**When** 使用者執行「重新載入設定」，**Then** 新的合法設定生效，不必重新安裝程式。
3. **Given** YAML 格式錯誤或值超出範圍，**When** 嘗試重新載入，**Then** 顯示可理解的錯誤並保留最後一份合法設定。
4. **Given** 程式正在顯示桌布，**When** 使用者按「離開」，**Then** 應用程式清理資源並恢復正常桌面狀態。

---

### User Story 4 - GPU 忙碌時自動延後下一張圖片 (Priority: P2)

使用者可以在 YAML 設定使用率門檻。平常程式靜態顯示現有桌布並等待下一次輪播期限；僅在期限到、準備開始下一張圖片時讀取一次系統整體 GPU 使用率。若負載過高，不啟動圖片動畫，保留目前桌布，直到未來某次繪製期限再次檢測合格。整個待機期間不設獨立負載監測程序或持續繪製；GPU 不可用的測試機可以使用系統整體 CPU 指標驗證相同狀態機。

**Why this priority**: 讓桌布程式在遊戲或 GPU 工作期間降低干擾，且不破壞原本的動態效果。

**Independent Test**: 注入可控時鐘及系統整體 GPU/CPU 高低負載讀值，驗證「未到繪製期限讀值次數為零」、「每次到期只檢測一次」、「高負載時不讀取下一張／不初始化過場」、「下次排程檢測合格才開始繪製」；在 WindowsEnv 使用 CPU 監測模式整合測試。

**Acceptance Scenarios**:

1. **Given** 下一次輪播時間尚未到期，**When** 桌布保持待機，**Then** 不採樣 GPU/CPU、不持續繪製新畫面、不預先消耗下一張圖片。
2. **Given** 下一張圖片的輪播期限已到，**When** 系統整體 GPU 使用率超過高負載門檻，**Then** 只檢查這一次，保留當前桌布，不選圖、不繪製過場。
3. **Given** 曾因高負載略過過場，**When** 自該次跳過時刻起經過完整的正常輪播間隔且新的單次負載讀值符合恢復門檻，**Then** 執行原本的完整動畫，不增加補播或改變公式。
4. **Given** 畫面過場已開始，**When** 動畫進行中，**Then** 不執行中途 GPU/CPU 負載抽樣，也不為了負載控制而截斷過場。
5. **Given** 無可用 GPU 的 WindowsEnv，**When** 使用 CPU 檢測模式並觸發繪製期限，**Then** 相同規則可由系統整體 CPU 使用率驗證。
6. **Given** 每次過場到期都因高負載遭跳過，**When** 依序略過三次，**Then** 每次都是距離前次判定完整輪播間隔後才重新檢查，不縮短間隔、不補播、不建立背景監測。

### User Story 5 - 共用不重複隨機圖片來源與空來源提示 (Priority: P1)

使用者在 YAML 指定共用圖片資料夾。應用程式以單一圖片提供者取得圖片，開場及所有螢幕的正常輪播都使用同一個序列。提供者先整理有效圖片、產生隨機但不重複的順序；一輪內每張最多選一次，直到此輪取完才重新掃描資料夾與建立下一輪順序。如果只有一張圖片，仍能在不同輪次重複使用完成開場。若完全沒有可用圖片，程式不渲染任何新圖片或開場動畫，系統匣保留操作功能並顯示「沒有圖片」。

**Why this priority**: 圖片序列正確性是正常輪播、多螢幕與新開場的一致性基礎；零圖片不得造成無限輪詢、黑畫面反覆重繪或無錯誤提示。

**Independent Test**: 使用固定隨機種子與假檔案系統，模擬 0、1、3、11、22 張圖片，檢查輪內無重複、輪完才重排並更新目錄；再使用系統匣測試 0 圖片狀態，確認圖片繪製呼叫數為 0。

**Acceptance Scenarios**:

1. **Given** 目錄內共有三張有效圖片，**When** 連續取出前三張，**Then** 每張各出現一次，第三張取出之前不得重複或重建該輪圖片清單。
2. **Given** 一輪已經取完，**When** 下次要求圖片，**Then** 重新掃描設定的圖片目錄並為新一輪建立不重複的隨機順序；上一輪中途新增的圖片於下一輪才會納入。
3. **Given** 只有一張有效圖片，**When** 多螢幕開場連續請求圖片，**Then** 每輪取出此圖一次，接著開始下一輪繼續使用，不減少每螢幕的預定背景張數。
4. **Given** 啟動時共有零張有效圖片，**When** 啟動程式，**Then** 不繪製主圖、背景圖或過場，系統匣仍可使用並清楚顯示「沒有圖片」。
5. **Given** 圖片在使用中被刪除或損壞，**When** 取圖失敗，**Then** 安全跳過失效檔案並回報錯誤，不陷入無限重試或觸發未經請求的持續渲染。
6. **Given** 有效圖片在開場後或正常輪播途中全部消失，**When** 後續無法取得下一張，**Then** 保留最後成功顯示的靜態桌布、停止新的圖片動畫並在系統匣提示「沒有圖片」。

---

### Edge Cases

- 圖片目錄不存在、暫時無圖片、圖片損壞或單張圖片損毀時不得造成當機或無限忙碌重試；格式副檔名正確不代表一定能成功解碼，無法解碼的檔案須略過並留有錯誤資訊。
- 有效圖片數為 1 到 `11 × 螢幕數 - 1` 時，必須取完一輪才開始下一輪，允許跨輪重複，確保每個螢幕仍能完成 1 張主圖加 10 張背景圖。
- 有效圖片數為 0 時不得建立任何圖片繪製工作，仍須保持系統匣可操作並顯示「沒有圖片」。
- 10 張背景圖片滑入時不可遮住已出現的主圖，任何尚未顯示的相片不得露出破碎貼圖或干擾使用者桌面圖示。
- 首次開場即使 GPU/CPU 負載過高也要完整執行；此例外僅限開場。開場後的正常輪播仍只在排定時間到期時檢查負載。
- 高負載持續數小時時不得反覆啟動動畫、持續重新解碼圖片、在待機時持續讀取使用率，或無限制增長記憶體。
- 使用率讀取失敗時需有可診斷、可預測的處置；不得把「沒有量測」當作 0%。
- 若讀取整體 GPU 使用率的資料需要短時間累積樣本，僅可在輪播期限到期後執行受限的單次量測，不可在待機時偷偷常駐輪詢。
- 螢幕有負座標、不同解析度或 DPI、顯示器熱插拔、Windows Explorer 重新啟動時必須能恢復正常桌布狀態。
- 設定檔讀取權限不足、未完成寫入或格式錯誤時，保留已驗證的前一份設定。
- 需避免背景長時間暫停時累積逾期輪播工作並在恢復時連續播放大量動畫。
- 目錄可能在一輪中途加入新檔，直到下一輪開始才應更新候選集；若既有檔案被移除、移動或變為無效，取圖失敗不得使程式當機或反覆消耗 CPU。
- 所有螢幕共用取圖輪次，不得因同時請求圖片而在同一輪重複選到相同路徑；背景滑入的時間隨機與圖片不重複抽取是兩個獨立需求。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 程式 MUST 支援 Windows 11 24H2 及更新版本，作為背景桌布運作而非前景浮動視窗。
- **FR-002**: 正常輪播的動畫公式、切換階段、圖片排版、挑選演算法與多螢幕行為 MUST 以 `master` 最新版 `Form1.MainLoop` 與 `Program.Main` 共有的動畫核心為等價性基準，並參考 `Form1` 的顯示配置變更處理；首次啟動階段是使用者已核准的獨立新設計，MUST NOT 因此改變後續正常輪播的動畫核心。詳見 `reference-audit.md`。
- **FR-003**: 多螢幕的選取 MUST 延續依螢幕面積加權的行為，所有螢幕 MUST 保留各自最後顯示的圖片。
- **FR-004**: 系統 MUST 支援既有的 JPG、JPEG、JFIF、PNG 圖檔及可設定圖片目錄。
- **FR-005**: 所有螢幕與開場／正常輪播 MUST 共用同一個圖片來源提供者與全域不重複隨機序列；一輪內不得重複同一圖片路徑，只有完成此輪才可開始新一輪。各螢幕 MUST 各自保留目前顯示狀態，並維持既有選擇螢幕的面積權重與動畫邏輯。
- **FR-006**: 程式 MUST 提供系統匣常駐、開啟 YAML、重新載入設定、手動暫停／繼續與結束程式功能；當可用圖片數為 0 時 MUST 清楚呈現「沒有圖片」的狀態，並保留重新載入設定及退出操作。
- **FR-007**: 程式 MUST 從 YAML 取得共用圖片來源、正常輪播間隔、系統整體 GPU 高負載暫停門檻、恢復門檻及相關資源負載控制參數；不得要求使用者在程式碼內修改這些數值，設定錯誤 MUST 可見且可復原。
- **FR-008**: 使用者 MUST 能在 YAML 設定高負載門檻、恢復門檻、正常輪播間隔，以及啟用／停用資源負載控制。MUST NOT 執行獨立的週期性使用率量測程序；正常輪播讀值時機僅由下一次圖片過場排程到期所觸發。
- **FR-009**: 高負載時 MUST 僅阻止尚未開始的下一次圖片過場，不得中止已在執行中的動畫；負載檢查 MUST 先於新圖片挑選、解碼及動畫提交。
- **FR-010**: 負載判斷 MUST 以系統整體 GPU 使用率作為正式 Windows GPU 環境的監測指標，不得僅用本程式自己的 GPU 使用率替代；無實體 GPU 的 WindowsEnv MUST 可用系統整體 CPU 使用率進行相同排程測試。
- **FR-011**: 當負載過高而跳過過場時，MUST 保持現有桌布與螢幕狀態；只有下一個允許的繪製期限到達後，單次量測符合恢復門檻才能開始新圖片；待機期間不得另行輪詢。
- **FR-012**: 程式 MUST 能處理螢幕配置變更、Windows shell/桌面重新啟動與正常退出時的資源清理。
- **FR-013**: 應用程式 MUST 在沒有使用者舊版硬編碼私人圖片路徑的情況下安裝與啟動。
- **FR-014**: MUST 提供可重現的動畫等價性測試、排程到期才執行一次 GPU/CPU 使用率檢查的測試，以及 WindowsEnv 整合驗證紀錄。
- **FR-015**: 輪播排程 MUST 能在靜態待機期間保持最低必要活動，下一次期限到期時才執行負載量測與新圖作業，且不得因錯過輪播而補播多個過場。
- **FR-016**: 當一次輪播期限到期且系統整體 GPU（或 WindowsEnv 的整體 CPU）使用率超過 YAML 設定的高負載門檻時，MUST 跳過當次過場，從這次判定／跳過時刻起等待 YAML 設定的完整正常輪播間隔，再到期時才重新讀取一次使用率；MUST NOT 使用更短的高負載重試間隔、在待機期間另設背景監測或在恢復時補播錯過的圖片。

- **FR-017**: 首次啟動 MUST 採用使用者批准的專用開場場景：在每個螢幕先呈現一張中央主圖，然後在該螢幕讓另外 10 張背景相片滑入主圖後方並逐步填滿背景，即每個螢幕共 11 張；MUST NOT 繼續使用舊版的「啟動時加速輪播數十張」方式模擬此視覺效果。
- **FR-018**: 每個螢幕開場的 10 張背景相片 MUST 有可控制範圍的隨機起始時間差，且多個滑入動作 MUST 能在時間上重疊；層級 MUST 位於各自的中央主圖後方，不能蓋住主圖；開場完成後 MUST 停止動畫繪製並回到正常待機／輪播排程。隨機範圍與滑入軌跡細節在 Plan 設計，但 MUST 可用固定種子重現作測試。
- **FR-019**: 多螢幕啟動時，MUST 在每一個螢幕各自安排一張中央主圖與 10 張背景圖片，總需求為 `11 × 螢幕數` 張（圖片足夠時）；啟動配額與舊版依螢幕面積加權選螢幕的全域快速換圖計數不同，屬使用者批准的新開場。MUST 不更動後續正常輪播的多螢幕面積加權選圖行為。

- **FR-020**: 首次啟動 MUST 忽略 YAML 高負載門檻，不因 GPU/CPU 使用率偏高而跳過或延遲各螢幕開場動畫；開場期間 MUST NOT 讀取 GPU/CPU 使用率，開場後只有正常輪播到期時才按 YAML 設定判定。
- **FR-021**: 當共用圖片來源有至少 1 張有效圖片、但不足 `11 × 螢幕數` 張時，啟動流程 MUST 繼續從同一個全域不重複隨機序列取圖；輪內不得重複，輪完後可從新一輪再次取得前一輪已用過的圖片，以完成每個螢幕 1 張主圖加 10 張背景的構圖；若沒有任何有效圖片，MUST 不進行圖片渲染並在系統匣顯示「沒有圖片」。

- **FR-022**: 應用程式 MUST 有獨立的圖片取得元件（參考原 C# `ImagePicker`），供啟動開場及正常輪播共用；它 MUST 負責讀取 YAML 設定的共用圖片目錄、依原版可支援的圖片格式整理候選、產生非重複的隨機輪次與依序提供下一張，不得把取圖邏輯複製進個別螢幕的渲染器。
- **FR-023**: 圖片取得元件 MUST 在啟動時掃描圖片來源，並在每輪所有候選用完、準備下一輪時重新掃描目錄並建立新的隨機順序，以反映新增／刪除的圖片；在每輪中間 MUST NOT 因固定輪詢而重置輪次。使用者從系統匣重新載入 YAML 並變更圖片來源時，MUST 重新初始化來源。原版 `Reset()` 只回到索引起點、`Next()` 每次計數檢查目錄，兩者均不是新版要求的輪次刷新行為。
- **FR-024**: 當全部設定來源都不存在或有效圖片總數為 0 時，啟動 MUST 不進行任何圖片與動畫繪製；系統匣 MUST 明確提示「沒有圖片」。如果運作途中圖片耗盡，MUST 停止新畫面繪製、保留最後成功呈現的靜態畫面並保持系統匣可操作；不得發生無限取圖重試、無止境重新掃描或錯誤彈窗風暴。
- **FR-025**: 取得圖片 MUST 對不存在、格式不受支援或解碼失敗的檔案安全跳過，並保留可診斷錯誤訊息；圖片未成功取得不得觸發動畫、不得將損壞圖像視為有效圖片，也不得破壞其他螢幕目前畫面。原版支援的副檔名為 JPG、JPEG、JFIF、PNG（不區分大小寫）。
- **FR-026**: 當啟動或運作時已進入「沒有圖片」狀態時，MUST 依 [NEEDS CLARIFICATION: 是否只在使用者於系統匣重新載入設定時掃描新圖片，還是每次正常輪播到期時也嘗試重新掃描一次以自動恢復？] 的規則判斷何時恢復；在沒有圖片時不得常駐掃描或空轉。

### Key Entities *(include if feature involves data)*

- **WallpaperSettings**：經驗證的目前設定，包含圖片來源、輪播、負載監測與使用者控制。
- **MonitorState**：螢幕識別、座標及尺寸、目前畫面與過場狀態。
- **StartupComposition**：每螢幕的一張中央主圖、10 張背景相片、滑入起始時間、層級、位置與完成後靜態畫面；所有螢幕共用圖片來源，開場不檢測 GPU/CPU。有效圖片不足時允許從下一輪重複使用，0 張則不繪製圖片。
- **ImageCandidate**：圖片路徑、支援格式、解碼結果、是否尚可在本輪選取。
- **ImagePickerQueue**：全螢幕共用的圖片取得元件，維護設定目錄、每輪候選圖片快照、隨機排列、目前索引、可用圖片數及零圖片狀態；啟動及每輪結束時重新整理來源。
- **ImageAvailabilityStatus**：圖片可用或「沒有圖片」狀態，供系統匣顯示與阻止沒有圖片時的畫面渲染。
- **UtilizationSample**：僅在輪播期限到期時取得的單次監測結果，包含來源（整體 GPU／整體 CPU）、數值、取得時間及有效性。
- **TransitionScheduler**：下一次到期時間、手動暫停／正常待機／因高負載跳過等狀態；只有到期才檢測資源負載，確保不補播過時過場。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 選定的 C# 基準實作所涵蓋的動畫公式及時間階段測試全部通過；數值比較容許誤差在測試方案中明示並經審核。
- **SC-002**: 使用固定隨機輸入及已知螢幕尺寸／位置的模擬測試，100% 符合參考螢幕選擇、圖片位置及狀態保存結果。
- **SC-003**: 以高、低、高、低、讀取失敗等模擬負載序列及虛擬時鐘測試，所有暫停與恢復案例皆符合預期；每次到期最多採樣一次，未到期採樣零次，跳過過場時新圖片選取與動畫繪製次數皆為零。
- **SC-004**: 在 Windows 11 測試機中可從系統匣完成修改設定、重新載入、手動暫停／繼續及離開的完整操作流程；錯誤 YAML 不造成程式異常終止。
- **SC-005**: 在 WindowsEnv 25H2 完成桌布整合及 CPU/軟體繪圖測試，另於具實體 GPU 及多螢幕的環境取得獨立驗證結果；未測項目須明示而不可宣稱通過。
- **SC-006**: 在等候下一次輪播時間的靜態待機測試中，GPU/CPU 使用率量測呼叫數與新圖片繪製呼叫數均為 0，且無獨立常駐監測程序。
- **SC-007**: 以可控時鐘連續模擬至少 3 次高負載略過過場，100% 的重新檢測時刻均不早於前次高負載判定時刻加上完整正常輪播間隔，未建立縮短重試或補播工作。
- **SC-008**: 以固定相片及固定隨機種子錄製單螢幕、雙螢幕開場：每個螢幕主圖 MUST 先行可見，接著各有 10 張背景圖片的滑入時段存在重疊且起始時間不完全一致，全部背景圖層位於各自主圖後方；圖片充足時單螢幕共 11 張、雙螢幕共 22 張；開場完成後動畫更新呼叫降為 0（正常待機狀態）。
- **SC-009**: 以模擬整體 GPU/CPU 使用率 100% 的測試環境啟動應用程式，主圖與各螢幕背景滑入 MUST 正常進行，開場期間負載量測呼叫次數為 0；首個正常輪播到期時才進行一次負載檢查。
- **SC-010**: 使用固定亂數種子測試擁有 1、3、11、22 張有效圖片的來源，每輪候選清單內每張圖片恰好提供一次，未輪完之前重複次數為 0；一輪結束後才更新新增或刪除的目錄圖片並開始新一輪。
- **SC-011**: 單螢幕僅有 1 張圖片或雙螢幕僅有 3 張圖片時，仍可分別完成 11 張或 22 張的啟動構圖；任何同一路徑的再次出現均發生在前一輪已完全用完之後。
- **SC-012**: 啟動時來源有 0 張有效圖片時，新圖片解碼、主圖與動畫繪製呼叫數均為 0，系統匣可看到「沒有圖片」且可操作；運作中圖片全數失效後，不破壞已呈現的靜態桌布，不產生高頻重試。

## Assumptions

- 第一版聚焦 Windows 11 桌面使用，不包含 macOS/Linux、雲端相片同步、線上相簿或影片桌布。
- 設定方式是系統匣操作搭配使用者可編輯的 YAML；目前不要求另做完整的圖形化設定視窗。
- 系統匣基本操作項目採一般桌布工具慣例作為初稿，待使用者複核。
- 首次開場是使用者指定的新設計，與原 C# 的快速初始化不同；每個螢幕 1 張主圖與 10 張背景照片，開場完全不檢測 GPU/CPU；正常輪播依然遵循舊版公式與負載檢查規則。
- 只有圖片取得元件負責選圖；輪內不重複，輪完後更新目錄與重排，跨輪允許重複，0 張則不渲染圖片並顯示「沒有圖片」。
- 圖片目錄掃描預設遵循原版 `Directory.GetFiles(folder)` 的非遞迴頂層檔案讀取，是否支援子目錄於規劃階段另列可選擴充，不應擅自改變來源範圍。
- 當圖片可用數為零，沒有已完成的輪次可供正常重置；恢復來源的觸發時間尚待使用者選擇。
- 舊版只保證全域快速切換次數與螢幕數量成比例，並非實際保證每螢幕各 10 張；新版將每螢幕數量明確固定，是使用者指定的新需求。
- GPU 高負載控制參數由 YAML 設定；此階段不替使用者固定高／低門檻預設值，也不增加週期性監測服務。
- 輪播及負載暫停門檻允許使用者設定，但不存在背景負載檢測間隔；具體門檻預設值及負載故障保護會於規劃階段提出、測試與審核。
- 高負載略過當次過場後，從該次判定時刻起使用完整正常輪播間隔排定下次嘗試，不進行縮短重試或補播（使用者已選擇 A）。
- 對應原始分支為 `master`（而非 `main`）；未完成 C++ 分支 `directx_build` 只用作 DirectX 技術參考。
- 無實體 GPU 的 WindowsEnv 可用軟體繪圖與 CPU 指標驗證程式路徑，但不代表實體 GPU 性能驗收已完成。
