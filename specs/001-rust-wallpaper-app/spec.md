# Feature Specification: YUAUY Wallpaper 完整桌布應用程式

**Feature Branch**: `rust_build`

**Created**: 2026-10-31

**Status**: Draft — 第三輪釐清排程策略

**Input**: 將 `master` 的 C# GDI+ 桌布樣品重製為 Rust + DirectX 的完整 Windows 11 桌布應用程式，保留既有動畫和多螢幕行為。所有螢幕共用相片來源，透過系統匣與 YAML 設定。平時維持靜態桌布並等待輪播時間到期；僅在準備開始下一張圖片的過場前檢測一次整體 GPU 使用率，超過門檻就跳過當次繪製，不建立獨立負載監測程序。WindowsEnv 25H2 使用 CPU/軟體繪圖驗證。

## Clarifications

### Session 2026-10-31

- Q: 舊版動畫的驗證參考是哪個入口？ → A: 使用者不確定；已靜態調查：`Form1.MainLoop` 與最新版 `Program.Main` 共有相同動畫核心（排除註解逐行一致），以該共同核心的公式、畫面操作和多螢幕規則為規格基準；`Form1` 的顯示配置更新為技術參考。現行啟動流程未能證實能自動輪播，不能將其視為已驗證；詳見 [舊版原始碼稽核](reference-audit.md)。
- Q: GPU 高負載的判斷範圍？ → A: 系統整體 GPU 使用率；WindowsEnv 沒有 GPU 時，改用系統整體 CPU 使用率進行測試。
- Q: 各螢幕圖片來源應如何分配？ → A: 所有螢幕共用一組圖片來源，各螢幕仍維持各自的畫面狀態與舊版的面積加權選取規則。
- Q: GPU 使用率何時檢測？ → A: 僅在等待到下一張圖片的預定繪製時間、準備進入過場前，當次檢測一次；待機期間不運行獨立負載監測／定期抽樣程序，也不做持續動畫繪製。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 保留舊版效果的 Windows 動態桌布 (Priority: P1)

使用者執行程式後，能在 Windows 11 桌面圖示後方看到輪播的圖片。每次切換保留既有動態效果與跨多螢幕的相片放置方式，而不是普通幻燈片。

**Why this priority**: 不還原舊版已驗證效果，Rust 重製就失去主要價值。

**Independent Test**: 使用固定圖片、固定隨機種子及單／雙螢幕幾何資料，比對最新版兩個 C# 入口共同的動畫核心之曲線、時間分段、畫面位置、轉換狀態及螢幕選取。再於 WindowsEnv 實際啟動 Rust 程式，確認桌布不是一般置頂視窗；舊版入口未直接驗證可正常自動輪播，須依原始碼稽核明確標示。

**Acceptance Scenarios**:

1. **Given** Windows 11 桌面與有效圖片來源，**When** 啟動應用程式，**Then** 在桌面圖示後呈現圖片而不妨礙其他視窗操作。
2. **Given** 多個尺寸與座標不同的螢幕，**When** 切換相片，**Then** 依既有螢幕面積加權規則選取目標螢幕，保留各螢幕已顯示圖片的狀態。
3. **Given** 固定的動畫進度與輸入參數，**When** 計算過場，**Then** 動畫的曲線、分段、平移、旋轉、縮放與覆蓋行為等價於舊版。
4. **Given** 顯示器接上、移除或變更解析度，**When** 顯示配置改變，**Then** 桌布重新建立正確的畫布，不遺留遮擋桌面的失效視窗。

---

### User Story 2 - 使用系統匣與 YAML 管理桌布 (Priority: P2)

使用者不需開著大型控制視窗即可常駐桌布程式；透過系統匣可檢視狀態、開啟設定檔、重新載入設定、暫停／繼續輪播，以及正常離開。圖片來源與輪播參數保存在 YAML。

**Why this priority**: 這是完整桌布工具與舊版實驗程式最大的使用體驗差異。

**Independent Test**: 在一台 Windows 11 電腦手動建立有效 YAML、從系統匣要求重新載入，再輸入無效 YAML 驗證錯誤回報與既有設定仍有效。

**Acceptance Scenarios**:

1. **Given** 使用者已有合法設定，**When** 開啟桌布程式，**Then** 設定生效且可在系統匣找到程式。
2. **Given** YAML 設定已編輯，**When** 使用者執行「重新載入設定」，**Then** 新的合法設定生效，不必重新安裝程式。
3. **Given** YAML 格式錯誤或值超出範圍，**When** 嘗試重新載入，**Then** 顯示可理解的錯誤並保留最後一份合法設定。
4. **Given** 程式正在顯示桌布，**When** 使用者按「離開」，**Then** 應用程式清理資源並恢復正常桌面狀態。

---

### User Story 3 - GPU 忙碌時自動延後下一張圖片 (Priority: P2)

使用者可以在 YAML 設定使用率門檻。平常程式靜態顯示現有桌布並等待下一次輪播期限；僅在期限到、準備開始下一張圖片時讀取一次系統整體 GPU 使用率。若負載過高，不啟動圖片動畫，保留目前桌布，直到未來某次繪製期限再次檢測合格。整個待機期間不設獨立負載監測程序或持續繪製；GPU 不可用的測試機可以使用系統整體 CPU 指標驗證相同狀態機。

**Why this priority**: 讓桌布程式在遊戲或 GPU 工作期間降低干擾，且不破壞原本的動態效果。

**Independent Test**: 注入可控時鐘及系統整體 GPU/CPU 高低負載讀值，驗證「未到繪製期限讀值次數為零」、「每次到期只檢測一次」、「高負載時不讀取下一張／不初始化過場」、「下次排程檢測合格才開始繪製」；在 WindowsEnv 使用 CPU 監測模式整合測試。

**Acceptance Scenarios**:

1. **Given** 下一次輪播時間尚未到期，**When** 桌布保持待機，**Then** 不採樣 GPU/CPU、不持續繪製新畫面、不預先消耗下一張圖片。
2. **Given** 下一張圖片的輪播期限已到，**When** 系統整體 GPU 使用率超過高負載門檻，**Then** 只檢查這一次，保留當前桌布，不選圖、不繪製過場。
3. **Given** 曾因高負載略過過場，**When** 之後的指定繪製期限到期且單次負載讀值符合恢復門檻，**Then** 執行原本的完整動畫，不增加補播或改變公式。
4. **Given** 畫面過場已開始，**When** 動畫進行中，**Then** 不執行中途 GPU/CPU 負載抽樣，也不為了負載控制而截斷過場。
5. **Given** 無可用 GPU 的 WindowsEnv，**When** 使用 CPU 檢測模式並觸發繪製期限，**Then** 相同規則可由系統整體 CPU 使用率驗證。

### Edge Cases

- 圖片目錄不存在、暫時無圖片、圖片損壞或單張圖片損毀時不得造成當機或無限忙碌重試。
- 高負載持續數小時時不得反覆啟動動畫、持續重新解碼圖片、在待機時持續讀取使用率，或無限制增長記憶體。
- 使用率讀取失敗時需有可診斷、可預測的處置；不得把「沒有量測」當作 0%。
- 若讀取整體 GPU 使用率的資料需要短時間累積樣本，僅可在輪播期限到期後執行受限的單次量測，不可在待機時偷偷常駐輪詢。
- 螢幕有負座標、不同解析度或 DPI、顯示器熱插拔、Windows Explorer 重新啟動時必須能恢復正常桌布狀態。
- 設定檔讀取權限不足、未完成寫入或格式錯誤時，保留已驗證的前一份設定。
- 需避免背景長時間暫停時累積逾期輪播工作並在恢復時連續播放大量動畫。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 程式 MUST 支援 Windows 11 24H2 及更新版本，作為背景桌布運作而非前景浮動視窗。
- **FR-002**: 動畫公式、切換階段、圖片排版、挑選演算法與多螢幕行為 MUST 以 `master` 最新版 `Form1.MainLoop` 與 `Program.Main` 共有的動畫核心為等價性基準，並參考 `Form1` 的顯示配置變更處理；對目前不會自動啟動輪播的入口問題，MUST 另以正常可用的 Rust 入口解決，不得改變動畫核心。詳見 `reference-audit.md`。
- **FR-003**: 多螢幕的選取 MUST 延續依螢幕面積加權的行為，所有螢幕 MUST 保留各自最後顯示的圖片。
- **FR-004**: 系統 MUST 支援既有的 JPG、JPEG、JFIF、PNG 圖檔及可設定圖片目錄。
- **FR-005**: 所有螢幕 MUST 共用一組圖片來源及既有的不重複隨機選圖序列；各螢幕 MUST 各自保留目前顯示狀態，並維持既有選擇螢幕的面積權重與動畫邏輯。
- **FR-006**: 程式 MUST 提供系統匣常駐、開啟 YAML、重新載入設定、手動暫停／繼續與結束程式功能。
- **FR-007**: 程式 MUST 從 YAML 取得圖片目錄、輪播時序與資源負載控制參數；設定錯誤 MUST 可見且可復原。
- **FR-008**: 使用者 MUST 能設定高負載門檻、恢復門檻，以及啟用／停用資源負載控制。MUST NOT 執行獨立的週期性使用率量測程序；讀值時機僅由下一次圖片過場排程到期所觸發。
- **FR-009**: 高負載時 MUST 僅阻止尚未開始的下一次圖片過場，不得中止已在執行中的動畫；負載檢查 MUST 先於新圖片挑選、解碼及動畫提交。
- **FR-010**: 負載判斷 MUST 以系統整體 GPU 使用率作為正式 Windows GPU 環境的監測指標，不得僅用本程式自己的 GPU 使用率替代；無實體 GPU 的 WindowsEnv MUST 可用系統整體 CPU 使用率進行相同排程測試。
- **FR-011**: 當負載過高而跳過過場時，MUST 保持現有桌布與螢幕狀態；只有下一個允許的繪製期限到達後，單次量測符合恢復門檻才能開始新圖片；待機期間不得另行輪詢。
- **FR-012**: 程式 MUST 能處理螢幕配置變更、Windows shell/桌面重新啟動與正常退出時的資源清理。
- **FR-013**: 應用程式 MUST 在沒有使用者舊版硬編碼私人圖片路徑的情況下安裝與啟動。
- **FR-014**: MUST 提供可重現的動畫等價性測試、排程到期才執行一次 GPU/CPU 使用率檢查的測試，以及 WindowsEnv 整合驗證紀錄。
- **FR-015**: 輪播排程 MUST 能在靜態待機期間保持最低必要活動，下一次期限到期時才執行負載量測與新圖作業，且不得因錯過輪播而補播多個過場。
- **FR-016**: 遇到高負載而跳過一次過場後，下次允許的繪製期限為 [NEEDS CLARIFICATION: 沿用正常輪播間隔等待下一次，還是為高負載跳過事件另外安排較短的重試時間？]；兩者都只能在排定期限到期時檢測，不可執行背景輪詢。

### Key Entities *(include if feature involves data)*

- **WallpaperSettings**：經驗證的目前設定，包含圖片來源、輪播、負載監測與使用者控制。
- **MonitorState**：螢幕識別、座標及尺寸、目前畫面與過場狀態。
- **ImageCandidate**：圖片檔案位置、可解碼尺寸及排序／選取狀態。
- **UtilizationSample**：僅在輪播期限到期時取得的單次監測結果，包含來源（整體 GPU／整體 CPU）、數值、取得時間及有效性。
- **TransitionScheduler**：下一次到期時間、手動暫停／正常待機／因高負載跳過等狀態；只有到期才檢測資源負載，確保不補播過時過場。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 選定的 C# 基準實作所涵蓋的動畫公式及時間階段測試全部通過；數值比較容許誤差在測試方案中明示並經審核。
- **SC-002**: 使用固定隨機輸入及已知螢幕尺寸／位置的模擬測試，100% 符合參考螢幕選擇、圖片位置及狀態保存結果。
- **SC-003**: 以高、低、高、低、讀取失敗等模擬負載序列及虛擬時鐘測試，所有暫停與恢復案例皆符合預期；每次到期最多採樣一次，未到期採樣零次，跳過過場時新圖片選取與動畫繪製次數皆為零。
- **SC-004**: 在 Windows 11 測試機中可從系統匣完成修改設定、重新載入、手動暫停／繼續及離開的完整操作流程；錯誤 YAML 不造成程式異常終止。
- **SC-005**: 在 WindowsEnv 25H2 完成桌布整合及 CPU/軟體繪圖測試，另於具實體 GPU 及多螢幕的環境取得獨立驗證結果；未測項目須明示而不可宣稱通過。
- **SC-006**: 在等候下一次輪播時間的靜態待機測試中，GPU/CPU 使用率量測呼叫數與新圖片繪製呼叫數均為 0，且無獨立常駐監測程序。

## Assumptions

- 第一版聚焦 Windows 11 桌面使用，不包含 macOS/Linux、雲端相片同步、線上相簿或影片桌布。
- 設定方式是系統匣操作搭配使用者可編輯的 YAML；目前不要求另做完整的圖形化設定視窗。
- 系統匣基本操作項目採一般桌布工具慣例作為初稿，待使用者複核。
- 輪播及負載暫停門檻允許使用者設定，但不存在背景負載檢測間隔；具體門檻預設值及負載故障保護會於規劃階段提出、測試與審核。
- 高負載跳過後的下次排程時間尚待使用者確認，在此之前不能把預設重試策略當成已核可。
- 對應原始分支為 `master`（而非 `main`）；未完成 C++ 分支 `directx_build` 只用作 DirectX 技術參考。
- 無實體 GPU 的 WindowsEnv 可用軟體繪圖與 CPU 指標驗證程式路徑，但不代表實體 GPU 性能驗收已完成。
